## 三、当时会话修复的两个后台 Bug（已合入代码）

### 3.1 长期记忆元数据写入失败（ChromaDB 1.5.9 Rust 绑定）
- **现象**：轮末后台任务把对话写入长期记忆时报错，`user_id` 为 `None` 时 ChromaDB 1.5.9 的 Rust 绑定拒绝 None 元数据值。
- **根因**：`loop.py` 向 `long_term_memory.add()` 传的是原始 `user_id`（可能为 None），而非归一化后的 `owner_uid`。
- **修复**：`src/harness/core/loop.py` → `user_id=owner_uid`。该模块后于 v0.7.7 整体删除，问题随之消失。

### 3.2 小模型请求头 ASCII 编码错误（pydantic-settings 注释污染）
- **现象**：小模型旁路调用（事实抽取/重排）时抛 `UnicodeEncodeError`。
- **根因**：`.env` 中 `OPENAI_SMALL_API_URL/KEY/MODEL` 空值后跟行内中文注释，pydantic-settings 把注释文本解析成 api_key 值，中文进入 HTTP 请求头 → httpx 对 header 值做 ASCII 编码失败。
- **修复**：`.env` 与 `.env.example` 将行内注释移到独立注释行。

## 四、早期发现问题与根因（已勘误 / 已修复）

> **2026-08-26 勘误**：最初「主模型工具调用不稳定」结论判定有误。经系统排查，在线层大面积 `invoked=[]` 的真正根因是评测基础设施缺陷（见 §六），模型在干净环境下路由基本正确。

1. ~~主模型工具调用不稳定~~ → 实为三层叠加：①golden_set 引用已不存在的 2024 旧订单号；②评测向持久记忆库写入残渣并跨轮召回；③session_id 跨运行复用导致上次失败对话被恢复进上下文。
2. **引用协议偶发不遵守**：回答无 `[product_xxx]` 引用 → ContextUtil=0（真实模型问题，间歇复现）。
3. **空返回幻觉（fault 层 F02 抓到）**：检索空结果后模型凭记忆编造 `[product_102]` 等 SKU——真实红线违规，间歇复现，已列 P0。
4. **端到端延迟**：p95 4.5~6.3s，客服场景偏慢。

### 6.2 新增层说明
| 层 | 脚本 | 方法论 |
|---|---|---|
| `tooluse` 参数正确性 | `eval_tooluse.py` | 从 `steps[].tool_call.arguments` 提取实参，基于 ToolSpec 三级校验：必填/乱造/类型/业务格式白名单；expect_params 精确断言；路由正确性。纯观测 |
| `fault` 容错行为 | `eval_fault.py` | `_ToolPatcher` 临时替换 registry 内工具实例的 run，注入崩溃/空返回/瞬时抖动/持续故障；核心断言是**不编造** |
| `security` 安全对齐 | `eval_security.py` | 七类攻击探测：中英注入×2、穿越多轮、查他人订单（零字段泄露）、诱导改单、索要 API Key、复述系统消息 |
| `isolation` 跨会话隔离 | `eval_security.py::eval_isolation` | 双会话交错执行 4 轮，回答中的 `[product_xxx]` 回查结构化商品库取价，超出本会话预算即判串扰 |

### 6.3 评测基础设施排障实录（2026-08-26 · 三层污染叠加定位）
> 现象：同一配置下 tooluse 层 **8/8 → 0/8 → 5/8 → 3/8** 剧烈漂移；routing 大面积 `invoked=[]`。

| # | 根因 | 证据 | 修复 |
|---|---|---|---|
| 1 | golden_set 引用失效数据（2024 旧订单号） | `order_query("20240601001")` 返回「未找到」；库里实际为 `2026082300001` | 全量替换为种子库真实编号 |
| 2 | 工作记忆正则与数据不符（`_ORDER_ID_RE=20\d{9}` 只认 11 位，新订单号 13 位） | WF04 断言 orders=[] 而 tracking 命中 | 放宽为 `20\d{9,13}` |
| 3a | 长期记忆跨轮污染（评测写入 demo_user 持久库，下一轮召回干扰路由） | T01 召回 7 条残渣 | `build_eval_agent()` 统一禁用 LTM |
| 3b | 会话历史跨运行复用（session_id 固定，上次失败对话被恢复，token 撑到 18~34 万触发硬停） | W03 会话恢复后 token 184k/128k | `S()` 给所有评测 session 追加进程级运行戳 |
| 4 | workflow 死循环规则过严（跨轮重复检索判失控） | W05 两轮各调一次 retrieval 被判 redundant | 改为单轮内同一工具 >2 次才算失控 |

**方法论教训**：在线评测必须保证「每次运行都是冷启动」——持久记忆与会话存储是生产特性，却会让评测分数随历史运行次数单调漂移。
