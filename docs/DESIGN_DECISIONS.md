# Agent Harness 设计决策文档

> 版本：v0.7.4 · 记录每个关键设计点的「为什么这样做」和「放弃了什么替代方案」
> 配合 [ARCHITECTURE.md](ARCHITECTURE.md)（是什么）和 [IMPLEMENTATION.md](IMPLEMENTATION.md)(怎么做) 阅读

## 一、总体架构决策

### 1.1 自研 ReAct 循环，不用 LangChain / LangGraph

**选择**：约 200 行 Python 实现完整 ReAct 循环。

**为什么**：
- LangChain 的 AgentExecutor 将循环逻辑封装在框架内部，出问题时需要读框架源码定位
- 我们需要精确控制每一步的行为：流式推送时机、失败重试策略、脱敏注入点、中断落盘时机——这些在 LangChain 中需要深入 callback 体系或自定义 Agent 类，复杂度不低于自研
- 自研后每个 bug 都能在一处修复（如 ACTION JSON 解析失败的纠正重试），不依赖上游版本更新

**放弃了什么**：LangChain 生态的 100+ 集成工具、现成的 Memory 抽象、社区支持。

**什么时候应该换**：如果项目需要接入 20+ 异构数据源或使用复杂的 Multi-Agent 协作模式，框架的抽象收益才开始超过控制成本。

### 1.2 SSE 而非 WebSocket

**选择**：Server-Sent Events 单向流式推送。

**为什么**：
- AI 回复是严格的单工流（服务端→客户端），无需双向通道
- 浏览器原生支持 EventSource API，无需额外库
- HTTP/1.1 即可工作，不需要协议升级
- 断线自动重连语义天然匹配「继续生成」

**放弃了什么**：双向通信能力（用户打断时无法服务端感知）。
实际通过 AbortController + 服务端 CancelledError 处理弥补。

### 1.3 SQLite 而非 PostgreSQL/MySQL

**选择**：SQLite WAL 模式作为业务库。

**为什么**：
- 单机部署零运维，无独立数据库进程
- WAL 模式下读写不互斥，满足当前并发模型
- 接口已通过 storage/db.py 抽象，迁移 PostgreSQL 只需替换连接层
- 演示阶段 400 商品 × 260 订单完全在 SQLite 舒适区内

**放弃了什么**：高并发写入、多机共享存储、高级查询能力。

**升级路径**：storage/db.py 的 SQL 均为标准语法，替换为 PostgreSQL 连接串即可。限流/风控计数器从进程内 dict 迁 Redis 需另行改造。

## 二、对话引擎设计决策

### 2.1 单气泡生命周期（前端）

**选择**：打字占位、流式增量、最终回答复用同一个 DOM 元素。

**为什么**：
- 早期版本用两个元素（typing bubble + final bubble），切换时出现重复头像、光标残留等视觉 bug
- 单元素方案下 delta 追加文本 → step 清空正文 → result 替换为 Markdown，状态转移清晰
- 中止路径只需处理一个元素的清理

**代价**：step 事件到达时会清空已流式的文本（该轮实为规划思考），但思考内容完整保留在时间线卡片中可展开查看。

### 2.2 token 统计：真实 usage > 双侧估算

**选择**：优先读取供应商返回的真实 usage；不可用时按 prompt+completion 双侧估算。

**为什么**：
- 流式响应默认不含 usage，需加 `stream_options.include_usage=true`（OpenAI v1 扩展）
- 仅估算 completion 侧会严重低估（system prompt + 历史窗口可能占总量 70%+）
- 双侧估算公式 CJK×0.7 + ASCII÷4 对主流分词器实测偏差 <15%

**放弃了什么**：完美精度。真实 usage 缺失时的估算仍可能有 ±20% 偏差，但对预算告警场景足够。

### 2.3 中断落盘而非丢弃

**选择**：用户停止生成或网络断开时，将已生成的部分对话和工作记忆保存到数据库。

**为什么**：
- 用户可能已经获得了有价值的部分回答
- 工作记忆中可能积累了预算约束等重要上下文
- 不落盘意味着下次进入会话丢失全部进度

**实现细节**：CancelledError 在 except 分支中调用 _persist_session 后 re-raise，保证向上层正确传播取消信号的同时完成持久化。

### 2.4 原生 function calling 协议（移除文本 ACTION 解析）

**选择**：统一走 OpenAI 原生 `tools` 载荷，模型结构化输出 `tool_calls`；无调用即视为最终回答，不再解析文本协议（ACTION / THOUGHT）。

**为什么**：
- 文本协议需 LLM 输出可被正则解析的 ACTION JSON，存在缺引号/多逗号/单引号等格式失败面，纠正重试治标不治本
- 原生 `tool_calls` 由推理服务端保证结构合法，参数 schema 随 `tools` 载荷原生携带——模型无格式自由，解析失败面归零
- 历史 `tool` 角色消息经 `_to_native_messages` 改写为 `user` 文本，适配无状态原生调用与严格校验型服务端
- 上游瞬时错误（超时/5xx）由 LLM 客户端指数退避重试兜底，而非格式纠正；空内容由输出护栏降级友好话术，绝不把残片当答案

## 三、记忆体系设计决策

### 3.1 为什么需要四层而不是一层向量库

| 层 | 解决的问题 | 如果去掉 |
|---|---|---|
| 工作记忆 | 「预算3000」在第 25 轮仍然生效 | 短期窗口截断后预算遗忘，推荐超预算商品 |
| 短期记忆 | LLM 需要最近对话的原始上下文 | 无近期消息，每轮都像首次对话 |
| 会话压缩 | 长对话超窗后早期信息永久丢失 | 第 30 轮时用户提到的订单号被彻底遗忘 |
| 长期记忆 | 跨会话知识（如用户偏好）无法积累 | 每次新会话都从零开始 |

**关键洞察**：这四层的生命周期和读写模式完全不同，强行合并到单一向量库会导致检索噪音和一致性灾难。

### 3.2 工作记忆用规则抽取而非 LLM 抽取

**选择**：正则表达式确定性提取预算/订单号/物流号。

**为什么**：
- 零延迟、零成本、100% 可预测
- 这些实体有强模式（数字+单位），正则准确率接近 100%
- LLM 抽取反而引入不确定性（可能漏抽或误抽）

**放弃了什么**：对非结构化偏好的抽取（如「我喜欢索尼」）。这类信息依赖 LLM 从对话中理解，不适合硬编码规则——现由轮末 LLM 抽取进 `important_facts` 事实层（见 3.5），且配合确定性预筛控制调用频率。

**边界处理**：「5000以下」是临时筛选不覆盖既有预算；「改成5000」才触发更新。区分这两者靠关键词「预算」「改成」的存在性判断。

### 3.3 会话压缩用「冻结章节追加」而非滚动摘要/全量截断

**选择**：单会话消息估算 token ≥ `CONTEXT_WINDOW_TOKENS × CONTEXT_COMPRESS_RATIO` 时，
把本周期较旧对话压缩为不可变章节【第 N 阶段】摘要 + 当期 WM 快照 → `chapters.append()`；
保留最近 `CONTEXT_KEEP_RECENT` 条原文（默认 20 条，摘要 ≤ `CONTEXT_SUMMARY_MAX_CHARS` 字）。

**为什么**：
- 简单截断 = 信息永久丢失（第 3 轮说的预算第 20 轮就忘了）
- 全量塞入 = 成本线性增长且受上下文窗口限制
- 摘要是信息论意义上的最优压缩：保留关键事实，丢弃寒暄和中间推理
- **LSM 式章节追加**：旧章节永不改写、只追加新章节——旧章节与系统提示词的 KV cache 永不失效；
  滚动合并旧摘要会有级联信息损耗，章节追加零级联
- **触发阈值按相对模型窗口**（`estimate_tokens` 启发式估算，非精确计数）而非消息条数——
  不同模型上下文窗口差异大（8k~256k），条数阈值无法适配；换模型只需调整
  `CONTEXT_WINDOW_TOKENS` 即可对齐触发时机

**压缩 prompt 要求必须保留的内容**：预算及品类 / 订单号物流号 / 已确认结论与承诺 / 未解决诉求。这是摘要质量的下界保障。

**降级策略**：LLM 摘要失败时保留完整历史不删任何内容——宁可 token 多花一些也不丢数据。

### 3.4 长期记忆按 user_id 隔离

**选择**：ChromaDB metadata 含 user_id，检索时 where 过滤。

**为什么**：多用户部署时 A 不应看到 B 的历史偏好。即使当前是单用户演示，架构上预留隔离能力避免了未来迁移时的数据清洗。

**距离阈值**：`LONG_TERM_MAX_DISTANCE` 超过阈值的历史视为不相关不注入，防止噪声污染 prompt。

### 3.5 成本与延迟：小模型旁路 + 抽取预筛 + 轮末后台化

**选择**：三招并用来压住「LLM 调用成本随轮次线性增长」与「收尾同步整理拖慢响应」：

1. **小模型旁路路由**：事实抽取、检索重排等旁路低风险调用优先走
   `OPENAI_SMALL_MODEL` 小模型（URL/KEY 留空继承主网关；MODEL 留空自动回落主模型），
   不占用主模型配额与限流。为什么不是全走主模型？旁路调用的输出不直接面对用户
   （质量要求低），用便宜模型显著降本；重排还同步缩小输入量
   （`RERANK_SMALL_TOP_N=8` < 主模型 `RERANK_TOP_N=20`）对冲小模型延迟。
2. **抽取预筛**：轮末先做确定性预筛（订单/物流/金额/预算正则、意图/偏好关键词、
   输入长度 ≥40 字），命中才调 LLM 抽取——纯寒暄/无信息轮零调用，进一步降频。
   为什么不做全 LLM 抽取？寒暄轮抽不出事实还白花钱，确定性预筛近乎零成本。
3. **轮末记忆整理后台化**：抽取→WM 合并→长期写入整体转入 `asyncio.create_task`，
   yield result 后立即结束 SSE 流。为什么不能同步？同步整理 2~4s 阻塞流关闭，
   前端「推理中」状态无法及时清除；后台化后下一轮执行前 `await` 上一轮落盘任务保证一致性。

**放弃了什么**：旁路调用彻底改用主模型（省事但贵）；每轮无条件 LLM 抽取（信息多但成本线性涨）；
同步整理后关闭流（实现简单但体验差）。

## 四、安全设计决策

### 4.1 输出脱敏前移到入库之前

**选择**：最终回答先过 OutputFilter 再写入短期记忆和会话历史。

**为什么**：
- 如果先入记忆再在输出时过滤，敏感信息已经进入了下一轮的 LLM 上下文
- 即使当轮输出被掩码，下一轮 LLM 可能从上下文中「回忆」出未掩码版本并输出

**影响**：记忆和历史中存储的是脱敏后的文本，后续轮次引用时也是安全的。

### 4.2 政策类问题强制查库而非让 LLM 回答

**选择**：policy_query 工具查结构化政策库（10 条 JSON），未命中明确告知并引导转人工。

**为什么**：
- LLM 编造退货政策（如「激活了也能退」）会造成直接资损
- 结构化条款可以精确引用编号，便于审计追溯
- 未命中时宁可不答也不编造，这是合规底线

**放弃了什么**：对模糊问题的灵活理解能力（如「我买了一个月了能退吗」需要结合具体商品类别判断）。当前通过引导转人工弥补。

### 4.3 订单归属校验在工具层而非 LLM 层

**选择**：order_query 工具内部比对 ContextVar user_id 与数据库 owner 字段。

**为什么**：
- LLM 层校验可以被 Prompt 注入绕过（「忽略之前的指令」）
- 工具层校验是确定性的代码逻辑，不受 LLM 输出影响
- 归属信息来自服务端 ContextVar 而非请求参数，不可伪造

**放弃了什么**：管理员代查场景需要额外的授权机制（当前不支持）。

### 4.4 枚举风控熔断而非仅限频

**选择**：同会话连续 8 次查询未命中即冻结该工具 30 分钟。

**为什么**：
- 正常用户不会连续输入 8 个都不存在的订单号
- 攻击者的目标是遍历有效 ID，熔断直接切断了这条路径
- 命中一次即清零计数，不影响正常使用

**放弃了什么**：误触发的可能性（连续手输错误 8 次）。30 分钟冷却期是可接受的代价。

## 五、前端设计决策

### 5.1 零依赖单文件而非 React/Vue

**选择**：所有 HTML/CSS/JS 内联在一个 index.html 中，无构建步骤。

**为什么**：
- 后端 FastAPI 直接 serve 静态文件，部署最简
- 无 node_modules、无 webpack/vite、无版本冲突
- 文件大小 ~40KB（含 CSS 和 JS），加载极快
- 代码量可控（~700 行 JS + ~300 行 CSS）

**放弃了什么**：组件化开发、状态管理、热模块替换。
当前功能规模下单文件的可维护性优于引入框架的学习和维护成本。

**升级路径**：如需扩展为大型 SPA，可将 CSS/JS 拆分为独立文件并用 Vite 构建，接口不变。

### 5.2 黑白双主题而非彩色渐变

**选择**：CSS 自定义属性定义两套灰阶配色，◐ 按钮一键切换。

**为什么**：
- 客服场景需要长时间阅读，高对比度黑白最不易疲劳
- 彩色渐变在演示时吸睛但在日常使用中干扰注意力
- 两套配色共享全部布局代码，切换零成本

### 5.3 思考过程默认折叠而非隐藏

**选择**：Agent 推理步骤以折叠卡片形式展示，点击展开 Thought/Action/Observation。

**为什么**：
- 完全隐藏会让用户觉得系统是黑盒
- 默认展开则信息过载（尤其多步任务）
- 折叠态显示步数统计和工具名摘要，感兴趣时展开看详情

### 5.4 流式输出的单元素生命周期

**选择**：打字占位、增量渲染、最终排版复用同一个 DOM 元素。

**为什么**：
- 多元素方案（占位气泡→正式气泡）在异常路径上容易出现残留光标、重复头像等视觉 bug
- 单元素方案下 finally 块统一清理，不可能遗漏

**代价**：增量渲染时不能使用完整的 Markdown 解析（性能考虑），最终 result 事件到达时整体重新渲染。

## 六、数据层设计决策

### 6.1 向量库定位为索引而非事实源

**选择**：SQLite 是商品的唯一事实源，ChromaDB 只是可随时重建的检索索引。

**为什么**：
- 向量库数据损坏时可从 DB 全量重建（reindex_all(prune=True)）
- 价格/库存等高频变动字段不进向量文本，避免每次变动都重嵌入
- 下架商品 = DB 删除 + 向量 delete 同步执行，杜绝残留

**对账机制**：reindex_all 以 DB id 集合为准，删除向量库中的脏 id。

### 6.2 商品 SKU 展开为独立条目

**选择**：同一手机的不同存储版本（256GB/512GB/1TB）作为独立商品记录。

**为什么**：
- 电商平台的真实做法就是按 SKU 管理
- 用户搜索「512GB」时应精准命中对应 SKU
- 价格因容量不同而异，合并记录会导致价格歧义

**代价**：目录条目数膨胀（62 手工款 → 400 条含变体），但检索评测证明 RRF 融合在 400 条规模下仍保持 13/13 满分。

### 6.3 会话历史进 SQLite 而非文件

**选择**：sessions/session_messages 双表替代旧版 JSON 文件。

**为什么**：
- JSON 文件的并发写覆盖、原子性（临时文件+replace）、损坏恢复都需要自行实现
- SQLite 事务天然保证原子性和一致性
- 过期清理变为一条 DELETE WHERE updated_at < ? SQL
- 旧版 JSON 文件首次启动自动迁移，零丢失升级

**放弃了什么**：直接打开文件人工检查内容的便利性。SQLite CLI 或 DB Browser 可替代。

## 七、评测体系设计决策

### 7.1 Ground Truth 运行时计算而非手工标注

**选择**：检索层的期望命中集合从 products.json 的结构化字段实时计算。

**为什么**：
- 手工标注的商品列表在目录变更后会静默失效（曾发生过：R06 要求 ≤6000 的游戏笔记本，目录中不存在）
- 结构化条件（价格≤X 且品类=Y 且标签含 Z）可直接翻译为 GT 过滤逻辑
- 新增商品自动纳入评测覆盖

**放弃了什么**：人工标注能捕捉的隐性相关性（如「拍照好」可能匹配 description 中未含「拍照」二字的商品）。
通过 keywords 匹配 tags+description 部分弥补。

### 7.2 预算合规为零容忍断言

**选择**：budget 层任何一条用例出现超预算推荐即整层 FAIL。

**为什么**：推超预算商品是客服场景的直接资损风险，不是概率问题而是底线问题。

### 7.3 badcase 回流闭环

**选择**：export_badcase.py 从审计 blocked 事件 + 失败轨迹自动导出候选用例。

**为什么**：线上暴露的问题如果不回流到测试集，同样的 bug 会在下次重构时复发。

## 八、已知取舍与未来方向

| 取舍 | 当前状态 | 未来方向 | 触发条件 |
|---|---|---|---|
| 进程内限流/风控/锁 | 单实例可用 | 迁移 Redis | 多副本部署时 |
| SQLite 单写者 | 当前并发足够 | PostgreSQL | 写入 QPS > 100 |
| 无认证体系 | X-User-Id 自报身份 | JWT/OAuth | 公网暴露前必须 |
| mock 物流/库存静态 | 演示可用 | 对接真实中台 API | 上线前必须 |
| 无多模态 | 纯文本 | 图片理解 | 有图片客服需求时 |
| jieba 未安装时内置分词器 | 二元组效果可接受 | 强制安装 jieba | 检索质量不满意时 |
