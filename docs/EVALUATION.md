## 二、检索质量评测（RAG 核心）

### 2.1 方法论

```
Ground Truth 计算：
  data/seed/products.json 结构化字段 → 运行时过滤
  条件：price_max / price_min / category / keywords(tags+description)
  ↓
期望命中集合 GT = {product_id | 满足全部约束}
  ↓
工具输出 top5 与 GT 取交集 → Recall@5 / MRR
  ↓
硬合规断言：top5 中每条商品的价格必须在 [price_min, price_max] 内
              品类必须精确匹配
```

**为什么不用手工标注**：目录从 62 扩到 400 时手工标注的 GT 会静默失效。结构化条件翻译为 GT 过滤逻辑后，新增商品自动纳入覆盖。

### 2.3 指标解读

**Recall@5 = 1.00（13/13）**

所有查询的 top-5 中都包含了至少一个 Ground Truth 商品。在 400 条目录下达到满分意味着：
- 向量语义 + BM25 关键字的 RRF 融合有效覆盖了不同表述方式的同义需求
- 意图词加成排序确保「拍照」→ 影像类、「游戏」→ 电竞类的强意图优先满足

**MRR = 平均 0.95**

13 条中 11 条 MRR=1.00（GT 第一位即命中），R05 MRR=0.33、R12 MRR=0.50 表示 GT 商品出现在第 3 和第 2 位——仍然在前三但不是第一。原因：预算接近度加权将「贴预算但不完全匹配关键词」的商品提前，属于业务正确的排序策略。

**价格品类硬合规 = 零违规**

每条查询的 top-5 中所有商品的 price 和 category 均严格落在约束范围内。这是通过 ChromaDB where 子句下推实现的——不在检索层过滤而在排序层惩罚会允许越界商品挤入。

### 2.5 RAG 生成质量评测（规划中）

当前 retrieval 层验证了召回质量，以下维度待接入：

| 维度 | 说明 | 评估方式 | 当前状态 |
|---|---|---|---|
| **Faithfulness（忠实度）** | 回答中的商品名/价格是否可追溯到检索结果 | 解析回答中的 [product_xxx] 引用，比对 DB 实际数据 | 引用格式已实现，评测脚本未写 |
| **Answer Relevance** | 回答是否切题（而非答非所问） | LLM-as-Judge 打分 1-5 | 需 --live 模式 |
| **Context Utilization** | 检索到的 top-K 中有多少被实际引用 | 回答中引用 id 数 / 检索返回数 | 可离线计算 |
| **Hallucination Rate** | 回答中出现但不在检索结果中的商品名/价格比例 | 名称匹配 + 价格交叉校验 | 可离线计算 |
| **Completeness** | GT 中排名前3的商品是否都被提及 | top-3 GT ∩ 回答中提到的商品集合 | 需 --live |

## 三、预算合规评测

### 3.1 为什么零容忍

推超预算商品是客服场景的直接资损风险。不同于检索排序可以容忍次优结果，预算违规是业务底线——用户说「3000 以内」就绝对不能推荐 ¥5000 的商品。

### 3.2 结果

| 用例 | 预算 | 返回价格 | 超预算数 | top1 接近度 |
|---|---|---|---|---|
| B01 预算3000以内拍照手机 | ≤3000 | 全部合规 | 0 | 0.93 |
| B02 只有2000预算买耳机 | ≤2000 | 全部合规 | 0 | 0.95 |
| B03 预算5000买笔记本 | ≤5000 | 全部合规 | 0 | 0.96 |
| B04 预算1500能打游戏的手机 | ≤1500 | 全部合规 | 0 | 0.93 |

**top1 接近度** = top1 商品价格 ÷ 预算上限。接近 1.0 表示推荐的正是贴近预算上限的最优选择（符合「让用户觉得钱花得值」的业务目标）。全部 >0.93 说明排序策略正确地将最接近预算的高性价比商品排在首位。

### 3.3 实现机制

预算约束通过三层保障：

```
① ChromaDB where 子句：{"price": {"$lte": budget}}     ← 向量检索层即排除超预算
② 意图词加成排序：命中意图词的商品优先                    ← 相关性保障
③ 预算接近度加权：0.6 × hybrid_score + 0.4 × proximity   ← 贴预算优先
```

三层叠加使得即使某一层出现边缘 case，整体仍保持零违规。

## 五、长期记忆召回评测

### 5.1 方法论

向临时 ChromaDB collection（cosine 空间）灌入 5 条带已知事实的历史对话，用自然语言追问验证语义召回：

| 查询 | 期望命中 | 实测 | MRR |
|---|---|---|---|
| 之前说过的买手机预算是多少来着 | m1(预算5000买拍照手机) | 第1位 | 1.00 |
| 我上次查的那个订单状态怎么样 | m2(订单已发货顺丰承运) | 第1位 | 1.00 |
| 记得我只信任哪个耳机的牌子吗 | m3(只买索尼耳机) | 第1位 | 1.00 |
| 去高原徒步该带哪块表 | m5(Garmin fenix 9 高原徒步) | 第1位 | 1.00 |

### 5.2 关键发现

BGE-small-zh 在短文本对话片段上的语义召回表现出色——即使用户换了一种说法（如「之前说过的预算是多少」vs 原文「我预算5000左右想买台拍照好的手机」），仍能精准命中对应记忆。

## 七、已知局限与改进方向

| 局限 | 影响 | 改进方向 |
|---|---|---|
| 400 条目录下的评测可能偏乐观 | 大目录下 RRF 头部排序压力更大 | 扩至 1000+ 商品复测 |
| routing 层未在线执行 | 不知道真实 LLM 的工具选择准确率 | 配置有效 key 后运行 --live |
| RAG 生成质量（Faithfulness/Hallucination）未量化 | 无法证明回答完全基于检索结果 | 增加 LLM-as-Judge 或引用交叉校验 |
| 对抗集仅 8 条 | 覆盖不了所有攻击模式 | 持续从 badcase 回流扩充 |
| 无负载测试 | 不知道并发上限 | Locust/k6 压测 |
| 无跨浏览器 UI 测试 | 仅验证 JS 语法 | Playwright 截图对比 |
